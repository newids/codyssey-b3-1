# 문제와 답변 — B3-1 학습 목표 대비 Q&A

> 사용법: 답을 가리고 질문만 보고 **말로** 설명해 본다. 핵심 5문항(§A)은 평가자가 가장 먼저 물을 질문이다.
> §B 는 심화·꼬리 질문, §C 는 흔한 오개념(틀리기 쉬운 것), §D 는 실무형 시나리오 문제.

## A. 핵심 5문항 (과제 목표 1:1 대응)

### A1. VPC, Subnet, Route Table, Internet Gateway 는 각각 어떤 역할이며 트래픽은 어떻게 이어지는가?
- **VPC**: 내 계정 안에 만든 격리된 가상 네트워크. CIDR(예 10.0.0.0/16)로 사설 IP 범위를 정한다. 집으로 치면 "울타리 친 땅".
- **Subnet**: VPC 를 가용영역(AZ) 단위로 쪼갠 조각(예 10.0.1.0/24). 인스턴스는 반드시 어떤 서브넷 안에 놓인다. "땅 위의 방".
- **Route Table**: 서브넷에서 나가는 패킷을 목적지 CIDR 별로 어디로 보낼지 정하는 표. `10.0.0.0/16 → local` 은 VPC 내부, `0.0.0.0/0 → igw` 는 "그 외 전부 인터넷으로". "방 문 앞의 이정표".
- **Internet Gateway**: VPC 에 하나 붙는 인터넷 관문. 사설 IP ↔ 퍼블릭 IP 를 1:1 로 바꿔 주며 수평 확장되어 대역폭 병목이 없다. "울타리의 대문".
- **흐름**: 인터넷 → IGW(퍼블릭→사설 IP 변환) → 라우트 테이블이 연결된 서브넷 → SG 검사 → 인스턴스. 나갈 때는 인스턴스 → 라우트 테이블 `0.0.0.0/0` 매칭 → IGW(사설→퍼블릭 변환) → 인터넷.
- 서브넷이 "퍼블릭"인 조건은 딱 하나: **연결된 라우트 테이블에 IGW 로 가는 경로가 있는가**.

### A2. Security Group 과 IAM 의 역할 차이는? 최소권한 원칙은 왜, 어떻게 적용하는가?
- **Security Group** = 네트워크 계층. "어떤 **IP/포트의 패킷**이 인스턴스에 들어오고 나갈 수 있는가". ENI 에 붙는 Stateful 가상 방화벽.
- **IAM** = API/관리 계층. "어떤 **사람·프로그램**이 어떤 AWS **API 호출**(인스턴스 생성, SG 수정…)을 할 수 있는가".
- 비유: SG 는 건물 출입문의 경비, IAM 은 건물 관리 시스템의 권한표. SG 를 아무리 잘 짜도 IAM 이 뚫리면 공격자가 SG 자체를 바꿀 수 있다.
- **최소권한 원칙(Least Privilege)**: 작업에 필요한 최소 권한만 부여. 이유 ① 자격증명 유출 시 피해 범위(blast radius) 축소 ② 실수로 다른 리소스를 지우는 사고 방지 ③ 감사·추적 용이.
- **적용법**: 루트 대신 IAM 사용자, AdministratorAccess 대신 EC2/VPC 작업만 Allow, 무관한 S3/RDS 와 비싼 NAT/ELB 는 Deny, 리전 조건(`aws:RequestedRegion`)과 인스턴스 타입 조건으로 범위 축소, MFA 활성화. SG 쪽에서는 80 만 전체 공개, 22 는 /32, 전체 포트 개방 금지.

### A3. 외부 요청이 EC2 의 웹 서버까지 도달하려면 어떤 설정이 필요한가?
세 가지가 **동시에** 있어야 한다.
1. **라우팅**: 서브넷에 연결된 라우트 테이블에 `0.0.0.0/0 → IGW`, 그리고 IGW 가 VPC 에 attach. (응답 패킷이 나갈 길이자, 퍼블릭 서브넷의 정의)
2. **퍼블릭 IP**: 인스턴스에 퍼블릭 IPv4(자동 할당 또는 Elastic IP). 없으면 IGW 가 변환할 주소가 없어 외부에서 지목할 수 없다.
3. **보안 그룹**: 인바운드에 TCP 80, 소스 0.0.0.0/0 허용. (NACL 은 기본 전체 허용이므로 건드리지 않았다면 통과)
4. 추가로 **서버 프로세스**(Nginx)가 0.0.0.0:80 에서 listen 하고 있어야 한다. 1~3 이 OK 인데 프로세스가 없으면 "connection refused".

### A4. 오류가 났을 때 로그/증상을 근거로 어떻게 원인을 찾고 조치하는가?
절차: **증상 정밀화 → 계층별 가설 → 가설마다 검증 명령 → 조치 → 재확인 → 재발 방지**.
- 증상을 정밀하게 구분한다. `timeout`(패킷이 버려짐 → SG/라우팅/IP 문제) vs `connection refused`(도달했으나 포트 닫힘 → 프로세스 문제) vs `permission denied`(SSH 인증 → 키/사용자명) vs `UnauthorizedOperation`(IAM).
- 바깥에서 안으로 가설을 세운다: 내 IP 바뀜? → SG 규칙? → 퍼블릭 IP 있음? → 라우트 테이블/IGW? → NACL? → 인스턴스 상태 검사(2/2 checks)? → OS 안에서 프로세스/포트(`ss -ltnp`)? → 앱 로그(`/var/log/nginx/error.log`, `cloud-init-output.log`)?
- 근거가 되는 로그: VPC Flow Logs(ACCEPT/REJECT), EC2 System log, cloud-init 로그, nginx 로그, CloudTrail(IAM 거부 기록), `aws sts decode-authorization-message`.
- 한 번에 하나만 바꾸고 재검증한다. 해결되면 "왜 처음에 빠졌는가"를 체크리스트로 만든다.

### A5. 클라우드 과금의 대표 요인은? 실습 리소스는 어떤 순서로, 왜 그 순서로 정리하는가?
- **대표 과금 요인**: ① 실행 중 인스턴스(시간당) ② **EBS 볼륨**(인스턴스를 Stop 해도, 인스턴스와 분리돼도 GiB·월 과금) ③ **연결되지 않은 Elastic IP**(시간당) ④ **NAT Gateway**(존재만으로 시간당 + 처리량) ⑤ ELB/ALB(시간당) ⑥ RDS ⑦ 스냅샷 ⑧ 아웃바운드 데이터 전송.
- **정리 순서 (의존성 역순)**: EC2 Terminate(Stop 아님) → EBS 잔여 볼륨 삭제 → EIP Release → NAT GW/ELB/RDS 삭제 → IGW Detach 후 Delete → SG 삭제 → Subnet → Route Table → VPC → 키페어.
- **왜 이 순서인가**: AWS 는 의존 리소스가 남아 있으면 삭제를 거부한다(`DependencyViolation`). IGW 는 attach 상태면 못 지우고, 서브넷에 ENI 가 남아 있으면 못 지우고, VPC 는 안에 뭔가 있으면 못 지운다. 또한 **과금되는 것(EC2, EBS, EIP, NAT)부터** 먼저 끊어야 작업 중 비용이 멈춘다.
- 마지막으로 Billing 대시보드 / Free Tier 사용량, `check-leftovers` 스크립트로 0 건 확인.

## B. 심화 · 꼬리 질문

**B1. Security Group 과 Network ACL 의 차이는?**
SG 는 인스턴스(ENI) 단위·Stateful·허용 규칙만·모든 규칙 평가. NACL 은 서브넷 단위·Stateless(응답 트래픽도 명시 허용 필요)·허용/거부 모두·번호 순 평가. 기본 NACL 은 전부 허용이므로 이번 미션에서는 SG 만 다룬다.

**B2. "Stateful" 이 정확히 무슨 뜻인가?**
인바운드로 허용된 연결의 **응답 패킷은 아웃바운드 규칙과 무관하게 자동 허용**(반대도 동일). 그래서 SG 아웃바운드를 전부 막아도 80 으로 들어온 요청의 응답은 나간다.

**B3. 퍼블릭 IP 와 Elastic IP 의 차이는?**
자동 할당 퍼블릭 IP 는 인스턴스 **중지/시작 시 바뀌고** 무료. EIP 는 고정이며 실행 중 인스턴스에 연결돼 있으면 무료(2024-02 부터는 사용 중인 퍼블릭 IPv4 도 시간당 과금됨), **연결 안 되어 있으면 과금**. 실습에선 자동 할당으로 충분.

**B4. Main route table 과 Custom route table?**
VPC 생성 시 자동 생성되는 main 은 명시적으로 연결되지 않은 모든 서브넷의 기본. 실무에선 main 은 건드리지 않고(local 만) 퍼블릭용 커스텀 테이블을 만들어 명시 연결하는 게 안전. main 에 IGW 경로를 넣으면 **이후 만드는 모든 서브넷이 퍼블릭**이 되는 사고가 난다.

**B5. IGW 와 NAT Gateway 의 차이는?**
IGW: 양방향, 퍼블릭 IP 필요, 무료. NAT GW: 프라이빗 서브넷의 **아웃바운드 전용**, 인바운드 불가, 시간당 과금. 이번 미션은 퍼블릭 서브넷 1개라 NAT 불필요 → 만들면 과금 + 요구사항 외.

**B6. 0.0.0.0/0 과 /32 의 의미는?**
CIDR 의 prefix 길이. /0 = 모든 IPv4, /32 = 단일 주소. SSH 를 /32 로 제한하면 그 IP 외에는 SYN 조차 응답받지 못한다.

**B7. 왜 전체 포트(0-65535) 개방이 위험한가?**
서비스 외 포트(DB 3306, Redis 6379, 관리툴 등)가 인터넷에 노출된다. 봇이 수 분 내 스캔하고 약한 인증·무인증 서비스는 즉시 침해된다. 또 SG 는 허용 규칙의 합집합이므로 한 줄이 전체를 무력화한다.

**B8. IAM User 와 IAM Role 의 차이는? 이번 미션에서 EC2 에 Role 이 필요했나?**
User 는 장기 자격증명(비밀번호/액세스 키)을 가진 사람·도구용. Role 은 임시 자격증명을 **맡는(assume)** 대상용(EC2, Lambda, 타 계정). 이번 EC2 는 AWS API 를 호출하지 않으므로 인스턴스 프로파일(Role)을 붙이지 않는 것이 최소권한이다.

**B9. 왜 루트 계정을 쓰면 안 되는가?**
루트는 권한 제한이 불가능하고(결제·계정 폐쇄까지) 키 유출 시 복구가 어렵다. 루트는 MFA 걸고 금고에 넣고, 일상 작업은 IAM 사용자/SSO 로.

**B10. `AmazonEC2FullAccess` 관리형 정책을 쓰면 안 되나?**
S3/RDS 는 안 들어 있으니 미션의 "무관한 서비스 금지"엔 걸리지 않지만, NAT/ELB/모든 인스턴스 타입/전 리전이 허용되므로 "필요한 작업 중심"에 비해 과하다. 커스텀 정책으로 Deny 와 조건을 걸어 좁히는 것이 평가 포인트.

**B11. 인스턴스 안에서 `curl http://localhost` 는 되는데 외부에서 안 된다면 어디를 보나?**
localhost 성공 = 프로세스·앱 정상. 남는 건 네트워크 경로: 퍼블릭 IP 유무 → SG 80 → 라우트 테이블/IGW → NACL. 그리고 Nginx 가 `127.0.0.1:80` 에만 listen 중인지 `ss -ltnp` 로 확인.

**B12. `curl` 이 timeout 과 connection refused 를 내는 차이?**
timeout: 패킷이 **버려짐**(SG/NACL/라우팅/방화벽/IP 없음). refused: 패킷이 호스트에 **도달했고 OS 가 RST** 를 보냄 = 포트에 listen 하는 프로세스 없음. 이 구분만으로 조사 범위가 절반으로 준다.

**B13. User data 는 무엇이고 언제 실행되나?**
인스턴스 첫 부팅 시 cloud-init 이 root 로 1회 실행하는 스크립트. 로그는 `/var/log/cloud-init-output.log`. 재부팅 시 재실행되지 않는다(기본).

**B14. 인스턴스를 Stop 하면 과금이 완전히 멈추나?**
아니다. 컴퓨트 요금은 멈추지만 **EBS 볼륨과 EIP 는 계속** 과금. 완전히 멈추려면 Terminate(+볼륨 삭제, EIP 해제).

**B15. Terminate 했는데 EBS 가 남는 경우는?**
볼륨의 `DeleteOnTermination` 이 false 인 경우(루트 외 추가 볼륨 기본값). 정리 시 Volumes 메뉴를 반드시 확인.

**B16. SSH 키를 잃어버리면?**
AWS 는 프라이빗 키를 보관하지 않아 재발급 불가. 인스턴스를 새로 만들거나, 볼륨을 떼어 다른 인스턴스에 붙여 `authorized_keys` 를 수정하는 복구 절차가 필요. 그래서 "안전하게 보관"이 제약 사항.

**B17. SSH 22 를 아예 안 열고 접속하는 방법은?**
AWS Systems Manager **Session Manager**(SSM Agent + Role 필요) 또는 **EC2 Instance Connect Endpoint**. 실무 권장이지만 이번 미션은 "SSH 접속 가능" 이 요구사항이므로 22 를 /32 로 제한.

**B18. 왜 리전을 서울로 고정하는가?**
레이턴시·데이터 주권도 있지만, 실습 관점에서는 **리소스가 흩어지면 정리가 누락**되어 과금이 생긴다. 콘솔은 리전별 화면이라 다른 리전의 인스턴스는 보이지 않는다.

**B19. t2.micro 와 t3.micro 의 차이, 프리 티어는?**
둘 다 버스터블(크레딧) 1 vCPU/1 GiB. t3 가 신형·저렴하며 unlimited 모드 기본(초과 시 과금 가능). 2025-07-15 이전 생성 계정은 12개월 750시간/월 무료, 이후 계정은 크레딧 기반 프리 플랜. 어느 쪽이든 micro 1대 + 8GiB 는 범위 내.

**B20. 퍼블릭 IP 자동할당을 안 켜고 만들었다면 사후에 어떻게?**
실행 중 인스턴스엔 자동 퍼블릭 IP 를 나중에 붙일 수 없다. Elastic IP 를 할당해 연결하거나 인스턴스를 재생성.

**B21. DNS hostnames 옵션은 왜 켜나?**
인스턴스에 `ec2-x-x-x-x.ap-northeast-2.compute.amazonaws.com` 퍼블릭 DNS 이름이 붙는다. 미션 필수는 아니지만 HTTPS 보너스나 가독성에 유용.

**B22. Nginx `/health` 를 `return 200 "OK"` 로 만든 이유는?**
파일 I/O·앱 로직 없이 프로세스 생존만 확인하는 가장 가벼운 엔드포인트. 로드밸런서/모니터링이 주기적으로 호출해도 부하가 없다. 고정 응답이라 자동 검증이 쉽다.

**B23. VPC Flow Logs 는 무엇이고 트러블슈팅에 어떻게 쓰나?**
ENI/서브넷/VPC 의 패킷 메타데이터(출발지·목적지·포트·ACCEPT/REJECT)를 CloudWatch Logs/S3 로 기록. SG 나 NACL 때문에 REJECT 된 패킷이 보이면 "네트워크 계층에서 막혔다"는 확정 근거가 된다. (활성화에 IAM 권한·CloudWatch 가 필요하므로 미션 정책엔 미포함. 서술로만 알아두면 됨)

**B24. CloudTrail 은 왜 언급되나?**
모든 API 호출 기록. IAM 권한 부족(`UnauthorizedOperation`)이 "누가 무엇을 호출했고 왜 거부됐는지" 남는다.

## C. 흔한 오개념 (O/X)

| 주장 | 정답 | 이유 |
|---|---|---|
| 서브넷 이름에 "public"을 붙이면 퍼블릭 서브넷이다 | X | 라우트 테이블에 IGW 경로가 있어야 퍼블릭 |
| IGW 만 attach 하면 인터넷이 된다 | X | 라우트 테이블에 0.0.0.0/0 → igw 가 있고, 그 테이블이 서브넷에 연결돼야 함 |
| SG 아웃바운드를 막으면 웹 응답도 못 나간다 | X | Stateful 이라 응답은 자동 허용 |
| SG 에 Deny 규칙을 추가할 수 있다 | X | SG 는 Allow 만. Deny 는 NACL |
| IAM 권한이 있으면 SG 를 통과한다 | X | 완전히 다른 계층. IAM 은 API, SG 는 패킷 |
| 인스턴스 Stop 하면 과금 0 | X | EBS·EIP 는 계속 과금 |
| Terminate 하면 모든 볼륨이 지워진다 | △ | DeleteOnTermination=true 인 볼륨만 |
| EIP 는 항상 무료다 | X | 미연결 시 과금, 현재는 사용 중에도 IPv4 요금 발생 |
| 퍼블릭 IP 는 재부팅하면 바뀐다 | X | 재부팅(reboot)은 유지, 중지/시작(stop/start)에서 바뀜 |
| `AmazonEC2FullAccess` 는 관리자 권한이 아니므로 최소권한이다 | X | 필요한 작업 범위를 초과. 조건·Deny 로 좁혀야 최소권한 |
| timeout 과 connection refused 는 같은 문제다 | X | 전자는 네트워크 차단, 후자는 프로세스 부재 |
| 루트 계정으로 해도 MFA 만 걸면 괜찮다 | X | 권한 제한 불가. 미션 제약 위반 |

## D. 실무형 시나리오 문제

**D1.** 브라우저로 `http://<IP>` 접속 시 무한 로딩 후 "응답 시간이 너무 깁니다". 인스턴스 안에서 `curl localhost` 는 200. 가장 먼저 볼 것 2가지와 명령은?
> ① SG 인바운드 80 규칙 유무: `aws ec2 describe-security-groups --group-ids <sg> --query 'SecurityGroups[0].IpPermissions'` ② 인스턴스 퍼블릭 IP 와 서브넷 라우트: `aws ec2 describe-instances --query '...PublicIpAddress'`, `aws ec2 describe-route-tables --filters Name=association.subnet-id,Values=<subnet>`. timeout 이므로 프로세스가 아닌 네트워크 계층.

**D2.** 어제까지 되던 SSH 가 오늘 `Connection timed out`. 서버는 Running, 아무것도 안 바꿨다.
> 내 공인 IP 가 바뀐 것(ISP DHCP, 카페 이동). `curl checkip.amazonaws.com` 으로 현재 IP 확인 후 SG 22 소스를 새 IP/32 로 교체. 재발 방지: 작업 시작 루틴에 IP 확인 추가, 또는 Session Manager 사용.

**D3.** `ssh: Permission denied (publickey)`.
> 네트워크는 통했다(timeout 아님). 원인: 잘못된 사용자명(Ubuntu=`ubuntu`, AL=`ec2-user`), 다른 키페어, `.pem` 권한 644(`chmod 400`). `ssh -v` 로 어떤 키를 제시했는지 확인.

**D4.** `aws ec2 run-instances` 가 `UnauthorizedOperation ... encoded authorization failure message` 를 낸다.
> IAM 정책 부족. `aws sts decode-authorization-message --encoded-message <msg>` 로 어떤 액션이 거부됐는지 확인(예: `ec2:RunInstances` 의 조건 불일치 — 인스턴스 타입이 micro 가 아님, 리전이 서울이 아님). 정책을 "필요한 그 액션만" 추가한다. 재발 방지: 정책 변경 이력을 문서화.

**D5.** 인스턴스 안에서 `sudo apt-get update` 가 멈춘다. `ping 8.8.8.8` 도 실패.
> 아웃바운드 불가 = 라우트 테이블에 `0.0.0.0/0 → igw` 없음, 서브넷이 main 테이블에만 연결, IGW 가 detach, 또는 퍼블릭 IP 없음 중 하나. `describe-route-tables` 로 연결 확인. SG 아웃바운드가 기본값(ALL)인지도 확인.

**D6.** `curl http://<IP>/health` 가 404.
> 네트워크·Nginx 는 정상(응답이 왔음). `/health` location 이 없거나 설정 파일이 적용되지 않음. `sudo nginx -t`, `sudo nginx -T | grep -A3 health`, `systemctl reload nginx`. Ubuntu 는 `sites-enabled/default` 가 우선권을 가질 수 있으므로 제거.

**D7.** 정리하려고 VPC 삭제를 눌렀더니 `DependencyViolation`.
> 안에 ENI/서브넷/IGW/SG 가 남아 있음. 순서: 인스턴스 terminated 확인 → ENI 삭제 → IGW detach·delete → 서브넷 → 커스텀 라우트 테이블 → 커스텀 SG → VPC. 콘솔의 VPC 삭제 대화상자가 의존 리소스를 나열해 준다.

**D8.** 월말 청구서에 $3 가 찍혔다. 전부 지웠다고 생각했는데.
> Billing → Bills 에서 서비스별 내역: 흔한 범인은 (a) 다른 리전에 남은 인스턴스/볼륨 (b) 미연결 EIP (c) 스냅샷 (d) NAT Gateway. 전 리전 검색은 `aws ec2 describe-instances --region <각 리전>` 반복 또는 **Resource Groups → Tag Editor** 에서 All regions 로 조회.

**D9.** 보안 담당자가 "SSH 22 를 0.0.0.0/0 으로 열어도 키 인증이니 괜찮다"고 한다. 반박하라.
> 키 인증이 강해도 ① 전 세계 봇의 무차별 접속 시도로 로그 오염·CPU 소모 ② sshd 취약점(예: 2024 regreSSHion) 노출 ③ 키 유출 시 어디서든 접속 가능. /32 제한은 비용 0 의 방어층. 미션도 명시적으로 금지.

**D10.** 한 줄로 설명: "클라우드는 그냥 빠른 컴퓨터가 아니라 네트워크·보안·IAM 이 묶인 환경"이란 말의 의미.
> 서버를 띄웠다고 서비스가 되는 게 아니라, 패킷이 지나갈 길(라우팅·IGW), 통과할 문(SG), 그것을 만지는 권한(IAM) 세 겹이 모두 맞아야 외부에서 접속되고, 그중 하나만 느슨해도 침해나 과금 사고가 난다는 뜻.
